# OAuth verification: the demo video and the scope justifications

Written 11 Sep 2026 for §8.6 / FR-1241's sensitive-scope verification, after the consent screen's
branding was saved (app name Latch, homepage and privacy policy on `ksyadav1978.github.io`,
Audience still *Testing*). Two parts: **the recording script**, and **the five justifications**,
ready to paste. Every button label below is quoted from `app/src/main/res/values/strings.xml`,
and every claim in a justification is traced to the code that makes the call.

**One recording serves three uses** — OAuth verification, any Play policy question about
notification access, and the homepage — so it is recorded **on a demo account, never your own**:
the consent screen, Google Calendar and Google Contacts all show the signed-in address, and the
homepage copy will be public.

---

## What Google asks the video to show (read 11 Sep 2026)

From Google's sensitive-scope verification help (`support.google.com/cloud/answer/13804565`):

- the end-to-end flow **including the OAuth grant**;
- **the complete consent screen**, with exactly the scopes being requested;
- the device language set to **English**;
- every place the app uses a requested scope;
- captions or narration saying which requirement each moment meets is recommended.

Upload it to YouTube as **Unlisted** and paste the link into the verification form.

## Before recording — about half an hour, once

**1. Record in a separate Android user, not in your own.** Pixel: *Settings → System → Users →
Add user*. This keeps your own notifications, contacts and Latch data out of the frame, and it
avoids wiping your real Latch install — a fresh setup is needed on camera, and the only other way
to get one is *Disconnect and delete everything* on your working copy.

**2. A demo Google account.** Create one (for example `latch.demo.<something>@gmail.com`) and add
it under **Google Cloud → Google Auth Platform → Audience → Test users** — while the audience is
*Testing*, no other account can sign in. Add it to the new Android user as its only account.

**3. Install the current build into that user.** It must be the build from `SRS 1.219` onward —
earlier builds say *"not Contacts"* on the sign-in screen, directly above a consent screen asking
for Contacts, and a reviewer would stop there.

```
./gradlew :app:installDebug
adb shell pm list users                                   # note the demo user's id
adb shell pm install-existing --user <id> com.latch.android
```

The **debug** build is the one to record: it signs in because the debug SHA-1 is registered.
A release build will not sign in until `docs/RELEASE.md` item 5 is done.

**4. Phone settings, in the demo user.** Language **English**. Google Calendar, Google Tasks,
Google Contacts, Google Keep and Google Chat installed and signed in as the demo account.
Screen recording: the Quick Settings *Screen record* tile, with *Show touches* on.

**5. The fixtures — all fictional, none from the card corpus.**

| For | What |
|---|---|
| Event | A Keep note reading `Board review on 8 October 2027 at 15:00` |
| Undo | A second note, `Site visit on 9 October 2027 at 11:00` |
| Reschedule | A third note, `Board review on 15 October 2027 at 15:00` |
| Task | A fourth note, `Pay insurance renewal by 14 October 2027` |
| Card | `testdata/demo/card-demo.png`, **printed** (a photographed monitor gives moiré). Meera Menon, Example Textiles Private Limited, `example.com`. Generated by `MakeDemoCard.java` beside it |
| Notification | Your own account in `chat.google.com` on the PC, to send the demo account two Chat messages on cue |

**Do not use Gmail as the notification source.** The sign-in screen now says *"Latch does not read
your Gmail"*; a video showing Latch reading a Gmail notification would contradict it on camera,
even though the listener reads a notification and not the mailbox.

**6. Rehearse once without recording**, then remove the demo account's Latch calendar, the
contact and the to-do, and clear Latch's data in the demo user (*Settings → Apps → Latch →
Storage → Clear storage*) so the recorded run starts from setup. Also remove Latch at
`myaccount.google.com/connections` for the demo account, so the consent screen appears in full.

## The script — about six minutes

Each scene: **what you do**, **what must be on screen**, and a **caption** to add in editing.
*If it looks wrong* is what failure looks like — stop, and re-record the scene rather than
explaining it in a caption.

### Scene 0 — title card (edit only)

Caption: **"Latch — Android app `com.latch.android`. Demonstrates the OAuth grant and the use of
each requested scope: calendar.events, calendar.calendarlist, calendar.calendars, tasks, contacts."**

### Scene 1 — the grant *(all five scopes)*

1. Open Latch. Setup shows **Step 1 of 3**, *"Connect your Google account"*.
2. **Hold two seconds on the permission list** — five lines, then *"Nothing else. Not Gmail, not
   Drive."*
3. Tap **Continue with Google**. Pick the demo account.
4. While in testing, Google shows *"Google hasn't verified this app"*. Tap **Continue**. Keep it in
   the video — cutting it looks like hiding it.
5. The consent screen: **show the app name "Latch", then scroll slowly through every permission**.
   If Google shows tick boxes, tap **Select all**. Tap **Continue**.

Caption: *"Consent screen: app name Latch, five scopes, shown in full."*

*If it looks wrong*: fewer than five permissions on Google's screen, or a sign-in error — the
demo account is not a test user, or the install is not the debug build.

### Scene 2 — choosing a destination *(calendar.calendarlist)*

1. Step 2, *"Where should captures go?"* Tap **Use my existing calendars**. *"Loading your
   calendars…"*, then the list.
2. Caption: *"calendar.calendarlist: the user's writable calendars, so they choose where captures
   go."*
3. Tap **Create a Latch calendar** (marked *Recommended*). Tap **Next**.

### Scene 3 — the task list, and creating the calendar *(tasks, calendar.calendars, calendar.calendarlist)*

1. Step 3, *"Which task list?"* — the lists load. Choose **My Tasks**. Tap **Finish**.
2. *"Finishing setup…"*, then Latch's home screen.
3. Caption: *"tasks: the user's task lists. calendar.calendars: creates the one Latch calendar,
   only now, on Finish. calendar.calendarlist: sets its colour."*
4. Switch to **Google Calendar**, open the side menu: a **Latch** calendar, in red.

### Scene 4 — a capture becomes an event *(calendar.events: create)*

1. Open Keep, the *Board review on 8 October 2027* note. Long-press, **Select all**, then choose
   **Latch** in the text menu (it may be under **⋮**).
2. Latch's sheet: **EVENT**, *8 Oct 2027, 3:00 pm*, destination chip **Latch**. Tap **Save**.
3. *"Saved to Latch"* and **Undo (10)** counting down. Let it run out.
4. Google Calendar → 8 October 2027 → open the event: the title, and the captured text in the
   description.

Caption: *"calendar.events: creates the event the user confirmed. The text was read on the phone."*

### Scene 5 — the same message twice *(calendar.events: read, Latch's own events only)*

1. Repeat Scene 4's selection and tap **Save**.
2. *"Already saved. Nothing was written again."* Google Calendar still shows **one** event.

Caption: *"calendar.events: Latch looks only for events it created itself, marked with a private
property, so a message is never saved twice."*

### Scene 6 — Undo *(calendar.events: delete, only what it just made)*

1. Capture the *Site visit on 9 October 2027* note. Tap **Save**.
2. Tap **Undo** while it counts down. *"Removed. Nothing was left in your Google account."*
3. Google Calendar → 9 October: empty.

Caption: *"calendar.events: Undo removes only the event Latch created seconds earlier."*

### Scene 7 — a reschedule *(calendar.events: update)*

1. Capture the *Board review on 15 October 2027* note.
2. The sheet offers *"This looks like a reschedule. "Board review…" is already saved for … Move it
   to …?"*. Nothing has been written yet. Tap **Update**.
3. Google Calendar: the event is on **15 October**, and 8 October is empty.

Caption: *"calendar.events: moves the user's own Latch event when they say so."*

### Scene 8 — a deadline becomes a to-do *(tasks: create)*

1. Capture the *Pay insurance renewal by 14 October 2027* note. The badge reads **TASK**. Tap
   **Save**.
2. Open **Google Tasks** → My Tasks: the to-do, due 14 October 2027.

Caption: *"tasks: creates the to-do the user confirmed."*

### Scene 9 — a business card becomes a contact *(contacts: read, create)*

1. Latch home → **Capture a business card**. The camera opens. Photograph the printed card, then
   confirm in the camera.
2. Latch's card sheet: the photo it read above, every field in its own box — name, company, job
   title, mobile, email, address, website. **Show them all.** Tap **Save contact**.
3. *"Saved to your contacts."* Let the Undo run out.
4. Open **Google Contacts**: Meera Menon.

Caption: *"contacts: before saving, Latch compares email addresses with the user's contacts, on the
phone, to see whether this person is already there. Nothing read is stored or sent. Then it creates
the contact the user confirmed."*

*If it looks wrong*: a field misread. Retake the photo straight on and filling the frame; do not
save a contact with a wrong name on camera.

### Scene 10 — the same person again *(contacts: read, update)*

1. **Capture a business card** again and photograph the same card.
2. One of two things happens, and both are correct: *"Already saved. Nothing was written again."*,
   or — if this photo read a field differently — an offer naming the field, the value now in Google
   and the value on the card, with **Update** and **Save as new** and nothing written yet. If the
   offer appears, tap **Update**, then **Undo** inside the ten seconds, and show the contact
   unchanged in Google Contacts.

Caption: *"contacts: Latch recognises a person already in the user's contacts. It updates only
fields the user ticks, and undoing an update restores the old values. Latch never deletes a contact
it did not just create."*

### Scene 11 — notification access, and the prominent disclosure *(no scope; Play's user-data policy)*

1. Latch home → **Settings** → scroll to **Ways to capture** → **Notification capture**.
2. *"Reading notifications"*: **scroll slowly through every paragraph** — what is read, why, that it
   stays in memory, that Latch only offers, that the message is not copied into the calendar, that
   nothing goes to a webhook. This screen is the prominent disclosure; it has to be legible.
3. Tap **Open Android's notification access settings** → Latch → allow → accept Android's warning →
   back.
4. Turn on **Let Latch read notifications**. Tap **Allow Latch to notify you** → Android asks →
   **Allow**.
5. From the PC, send the demo account a Chat message with no date: *"Hi — are you free next week?"*.
   Back in Latch, **Which apps** now lists **Chat**. Tick it.
6. Send a second Chat message: *"Parent-teacher meeting on 16 October 2027 at 10:00"*.
7. A quiet notification: *"A date in a message. Capture it?"* Tap it → Latch's sheet → **Save**.
8. Google Calendar → 16 October → open the event: **the message text is not in it**.

Caption: *"Off by default. Enabled only through this disclosure. Read in memory. Only the apps the
user ticks. Latch offers; the user decides. The message is not copied into the calendar."*

### Scene 12 — deleting everything *(the grant, revoked)*

1. Settings → **Disconnect Google and delete everything on this phone** → **Yes, disconnect and
   delete**.
2. *"Disconnected. Everything Latch kept on this phone is gone."*
3. On the PC, `myaccount.google.com/connections` for the demo account: Latch is gone.

Caption: *"One action revokes Latch's access and deletes its local data. Items in the user's
Google account stay there — they are the user's."*

### Scene 13 — optional: Windows *(same Cloud project only)*

If the Windows OAuth client is in the same Google Cloud project, add half a minute: sign in from
the tray, and **show the browser's address bar on Google's consent page** — it carries the
`client_id`, which reviewers sometimes ask to see and which an Android consent screen never shows.
The Windows client asks for four scopes, not five: it has no business-card feature.

## The scope justifications — paste-ready

Google's form asks, per scope, how it is used. Each text below is what Latch does, with no more
access than it says. **Why not narrower** follows each one, because Google's scope documentation
asks for the narrowest scope that works (`developers.google.com/workspace/calendar/api/auth`).

### Overall app description

> Latch turns dates that a user selects or shares on their phone — in a message, a web page, a
> screenshot or a PDF — into entries in their own Google Calendar and Google Tasks, and turns a
> business card they photograph into a contact in their own Google Contacts. All text is read on
> the device; Latch has no server, and nothing is sent anywhere except to the user's own Google
> account. Every entry is shown to the user and confirmed before it is written, and every save can
> be undone for ten seconds.

### `https://www.googleapis.com/auth/calendar.events`

> Latch creates the calendar event the user has confirmed on Latch's confirmation screen, in the
> calendar the user chose. Before writing, it searches that calendar for an event Latch itself
> created earlier from the same text — identified by a private extended property Latch wrote on
> it — so that capturing the same message twice does not create a duplicate. When the user
> captures a message whose date has changed, Latch offers to move the existing Latch event, and
> changes its dates only if the user accepts. When the user taps Undo within ten seconds of
> saving, Latch deletes the event it has just created, or restores the dates of one it has just
> moved. Latch does not list, display or analyse the user's other events.
>
> Why not a narrower scope: the user chooses which calendar their captures are saved to, and may
> choose any calendar they can write to, including one shared with them that they do not own,
> such as a family calendar. calendar.events.owned would exclude shared calendars, and
> calendar.app.created would confine the user to a calendar Latch made.

Traced to: `insertEvent`, `findEventBySourceHash` (`eventDedupUrl`, `findEventPaged`), `findEventByItemKey`, `patchEventDates`,
`deleteEvent` in `:google`; FR-801, FR-803, FR-804, FR-807, FR-901.

### `https://www.googleapis.com/auth/calendar.calendarlist`

> Latch reads the user's calendar list so that the user can choose where their captures are saved,
> during setup and in Settings, and so that the chosen calendar's name and colour are shown on the
> confirmation screen before anything is saved. Only calendars the user can write to are offered.
> Latch writes to the calendar list in two cases, both at the user's request: when it creates its
> own Latch calendar it sets that calendar's colour, and if the user picks a calendar that is
> hidden in Google Calendar and asks Latch to turn it on, it makes that calendar visible so saved
> items are not invisible.
>
> Why not calendar.calendarlist.readonly: setting the colour and making a chosen calendar visible
> are writes to the calendar list.

Traced to: `listWritableCalendars` (`users/me/calendarList`), `setColourAndVisibility` and `makeVisible` (its two `PATCH` calls) in
`GoogleRest.kt`; FR-104, FR-901, FR-903, FR-904.

### `https://www.googleapis.com/auth/calendar.calendars`

> Used for two calls. During setup the user can choose "Create a Latch calendar", which creates a
> single secondary calendar named Latch to hold everything Latch saves, so the user can show, hide
> or remove all of it at once. It is created only when the user taps Finish; leaving setup earlier
> creates nothing. Latch also reads the user's primary calendar once, to learn which Google
> account the user signed in with, because Latch requests no profile or email scope. Latch never
> changes the properties of any existing calendar.
>
> Why not calendar.calendars.readonly: it cannot create a calendar.

Traced to: `createLatchCalendar` (`POST calendars`) and the `GET calendars/primary` identity read in `GoogleRest.kt`; FR-102, FR-105, AC-16.

**A reviewer may ask why not `calendar.app.created`, and that question is real.** That scope can
create a secondary calendar and write to it. `calendar.events` would still be needed for the
user's own calendars, and the primary calendar's id is also in the calendar list, so
`calendar.calendars` could in principle be replaced by `calendar.app.created`. **This has not
been tried**, and it is not a wording change: it changes the scope set, which SRS 1.87 records
invalidates every existing grant, and whether a calendar created by the Android client counts as
"created by this app" for the Windows client (FR-1002's adoption rule) is unknown. If a reviewer
raises it, the answer is a slice and a device pass, not a sentence.

### `https://www.googleapis.com/auth/tasks`

> Latch saves a deadline that has no time of day as a Google Tasks to-do. It lists the user's task
> lists so the user can choose one during setup and in Settings, and creates the to-do the user
> confirmed. Because the Tasks API cannot search by content, Latch checks for a duplicate by
> reading the tasks in the chosen list that are due within a day of the new one and comparing
> them on the phone against a marker line Latch adds to the notes of every task it creates; what
> it reads is not stored or sent. When the user accepts an offer to reschedule a Latch to-do,
> Latch changes its due date, and when the user taps Undo within ten seconds, Latch deletes the
> to-do it has just created or restores the one it has just changed.
>
> Why not tasks.readonly: Latch's purpose is to create to-dos.

Traced to: `listTaskLists`, `insertTask`, the ±1-day scan in `findTaskBySourceHash`, `findTaskByItemKey`,
`patchTaskDates`, `deleteTask`; FR-802, FR-803, FR-804, FR-807.

### `https://www.googleapis.com/auth/contacts`

> Latch turns a business card the user photographs into a contact in their own Google Contacts,
> after showing the user every field to check. The card is read on the phone and the photo is not
> kept. Before saving, Latch reads the email addresses of the user's existing contacts and compares
> them on the phone, to tell whether the person on the card is already there; nothing read is
> stored or sent anywhere. Latch then creates the contact the user confirmed. If the person is
> already a contact and the card shows different details, Latch reads that one contact and shows
> the user each field that differs; it updates only the fields the user ticks. If the user ticks
> "Use this photo as the contact's picture", Latch sets it. Latch deletes a contact only when the
> user taps Undo within ten seconds of Latch creating it; undoing an update restores the previous
> values. Latch never deletes any other contact.
>
> Why this scope: the People API has no create-only scope. contacts.readonly cannot create or
> update a contact, and contacts.other.readonly covers a different list.

Traced to: `connectionsUrl` (`personFields=clientData,emailAddresses`), `createContact`,
`getContactUrl` (`names,organizations,phoneNumbers,emailAddresses,addresses,urls`),
`updateContact`, `updateContactPhotoUrl`, `deleteContactUrl` from the undo path only;
FR-1208, FR-1209, FR-1226, FR-1231, FR-1232, FR-1102.

## Two findings from the research, recorded

**Play has no declaration form for notification access (checked 11 Sep 2026).** The Play Console
declaration form covers SMS and call log, background location, all-files access,
`QUERY_ALL_PACKAGES`, accessibility, `REQUEST_INSTALL_PACKAGES`, Health Connect, and exact alarms
and full-screen intents — not notification listeners (`support.google.com/googleplay/android-developer/answer/16558241`).
What governs Latch is the user-data policy's **prominent disclosure** rule, which
`NotificationAccessScreen` already meets: in the app, before the permission, in normal use, saying
what is accessed and why. So FR-1104's "justify in the Play Console" has no form to go in today;
Scene 11 is the evidence if a reviewer asks.

**The merged manifest carries `FOREGROUND_SERVICE` with no service type**, from WorkManager's
`SystemForegroundService`, which Latch never starts in the foreground. Play's foreground-service
declaration is keyed to typed foreground-service permissions, so it is not expected. If the
Console asks anyway, the answer is that no foreground service type is declared or used.
